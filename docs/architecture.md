# Architecture

GhostShift AI is a local-first monolith: a Micronaut HTTP API, a Vue single-page app, a SQLite database, and an optional Ollama runtime. There is no cloud control plane and no hosted model provider.

```text
┌──────────────────────────────┐
│ Vue 3 + TypeScript SPA       │
│ Router · Pinia · fetch       │
└──────────────┬───────────────┘
               │ /api/v1 (REST + SSE)
┌──────────────▼───────────────┐        ┌────────────────────────┐
│ Micronaut 5 / Java 25        │───────▶│ Ollama /api/chat       │
│ Controllers → Services       │        │ local open-weight model│
└──────┬───────────┬───────────┘        └────────────────────────┘
       │           │
       │           └──────────────────▶ registered folders
       │                                (bounded read; guarded move)
┌──────▼───────────┐
│ SQLite (WAL)     │
│ plans · runs ·   │
│ reports · events │
└──────────────────┘
```

## Runtime components

| Component | Responsibility |
| --- | --- |
| `backend/` | Java 25 + Micronaut 5 API, workflow engine, SQLite access, Ollama adapter |
| `frontend/` | Vue 3 + TypeScript + Vite SPA, Pinia state, accessible dark/light design system |
| Ollama | Optional local inference at `http://localhost:11434` by default |
| SQLite | Durable local state at `<data-dir>/ghostshift.db` |
| `<data-dir>/reports` | Markdown reports generated by GhostDev/workflows |
| `<data-dir>/demo/inbox` | Synthetic demo files created on first startup |

The backend binds to `127.0.0.1:8080` by default. The Vite dev server proxies `/api` to that origin, so the browser only talks to one origin.

## Backend packages

```text
ai.ghostshift
├── ai/          Ollama adapter, prompt construction, validated AI results
├── api/         Micronaut controllers, optional token filter, error contract
├── config/      Immutable paths and hard limits
├── db/          Explicit JDBC access and the versioned migration runner
├── domain/      @Serdeable records, enums, and status constants
├── service/     Module logic, safety, execution, reports, demo data
├── util/        JSON, text, and filesystem boundary helpers
└── workflow/    Closed action registry, validator, persisted run context
```

There is no ORM and no connection pool. SQLite is a single-user local database, so every operation opens a short-lived connection in WAL mode with a busy timeout. Transactions are explicit. The `Database` class owns migration discovery and execution; migrations are plain SQL resources under `src/main/resources/db/migration`.

## Request flow

1. A Vue view calls `frontend/src/api/client.ts`.
2. A Micronaut controller accepts a typed request body.
3. The service validates limits, permissions, and state transitions. Safety checks are in the backend, not only in the UI.
4. A SQLite transaction records the durable state change.
5. Activity entries and run events are appended for history.
6. Long-running work is submitted to a bounded local worker (`JobRunner`) and the API returns immediately.
7. The UI polls run/plan state, or a client may subscribe to the run event SSE endpoint.

Errors use one JSON contract (`code`, `message`, `details`, `requestId`, `timestamp`). Stack traces are logged locally, never returned to the client. Every error response carries an `X-Request-Id`.

## Module implementation

### GhostSort

`OrganizationService` implements a deliberate pipeline:

```text
scan → classify → propose destination → preview conflicts
     → human decisions → execute with re-checks → record → optional undo
```

- The scanner is bounded by depth and file count, does not follow symlinks, and skips dependency/version-control directories.
- Classification uses deterministic filename rules first. The local model is optional and only sees filenames, extensions, and sizes for ambiguous files.
- Destinations are computed by application code from the configured category folder names. A model cannot supply a path.
- A plan remains `READY_FOR_REVIEW` until the user decides which actions are approved.
- Execution re-validates the source size and modification time, refuses overwrites, and records recovery metadata for each move.
- Undo only restores a file when the destination still matches the recorded size/hash fingerprint and the original path is free.

### GhostDev

`LogAnalyzer` parses text deterministically: severity counts, timestamp range, grouped error signatures, and line evidence. `DeveloperService` always produces a report from that evidence. If AI is enabled, the model may add a summary, hypotheses, and checks, but malformed or unavailable output falls back to deterministic content and says so in the report.

### GhostCapture

`RecordingService` records an explicit sequence of allowlisted file actions against a registered folder. Steps can be paused, edited, reordered through deletion/re-addition, and saved as a workflow draft. This is **file-action recording, not browser event capture**. No browser extension, screen recording, or DOM instrumentation is included.

### GhostReplay

`WorkflowService` stores immutable versions of workflow definitions. Editing an approved workflow creates a new version and resets approval. `WorkflowValidator` rejects unknown actions, unknown parameters, missing directory inputs, duplicate step IDs, and moves without a preview/approval path.

`RunService` creates a durable run and submits it to `RunExecutor`. The executor:

- loads the exact workflow version used by the run;
- executes only registry actions;
- enforces approval gates in the engine;
- supports dry runs that do not touch files or save reports;
- persists context between steps so an approval pause can resume;
- checks cancellation between safe actions;
- marks interrupted `QUEUED`/`RUNNING` runs as failed after a restart rather than silently resuming them.

### GhostBrain

`GhostBrainService` owns three AI-shaped tasks:

1. classify ambiguous filenames;
2. interpret bounded, deterministic log evidence;
3. draft a workflow from the action catalog.

Every response is treated as untrusted data. The service extracts JSON, maps it onto a closed schema, rejects unknown actions/categories, and never lets model text become a command, permission, path, or shell invocation.

### GhostPulse

`InsightService` aggregates dashboard counts, time-savings estimates, and duplicate reports. Duplicate detection is read-only: exact duplicates are confirmed by SHA-256; similar names are labeled as a separate, weaker signal and are never described as proof of identical content. Files over 100 MB are skipped for hashing.

## Workflow lifecycle

```text
DRAFT ──edit/validate──▶ READY_FOR_REVIEW ──approve──▶ APPROVED
  ▲                              │                        │
  └────────── edit ──────────────┘                        │ run
                                                          ▼
                                               QUEUED → RUNNING
                                                   │        │
                                                   │        ├─▶ WAITING_FOR_APPROVAL
                                                   │        │        │ approve
                                                   │        │        └──────▶ RUNNING
                                                   │        │
                                                   │        └─▶ COMPLETED / PARTIALLY_COMPLETED
                                                   └──────────▶ FAILED / CANCELLED
```

A workflow must be `APPROVED` for a real run. Dry runs are allowed while under review. A run that pauses for approval holds its persisted context and resumes on the same version. Rejecting an approval cancels the remaining steps.

## Data model

| Table | Purpose |
| --- | --- |
| `registered_directory` | The only folders GhostShift may read/organize |
| `organization_plan`, `organization_action` | GhostSort preview and per-file decisions |
| `workflow`, `workflow_version` | Workflow metadata and immutable definitions |
| `workflow_run`, `action_execution` | Durable run and step state |
| `run_event` | Ordered event log used by polling and SSE |
| `approval_request` | Human gates and resolutions |
| `file_operation` | Move/undo recovery metadata |
| `report` | Generated Markdown and evidence |
| `recording`, `recorded_step` | GhostCapture sessions |
| `classification_memory` | User-approved category corrections |
| `model_configuration` | Ollama endpoint/model/timeouts |
| `user_preference` | Theme, onboarding, policies, folder names |
| `activity` | User-facing history feed |
| `schema_migration` | Applied migration versions |

Timestamps are ISO-8601 UTC strings. JSON blobs are written through the application's `Json` helper and parsed back into typed records.

## Frontend architecture

- `src/router.ts` defines the ten workspace sections, the bare welcome route, run detail, and a 404.
- `src/stores/session.ts` bootstraps settings, AI status, dashboard, approvals, directories, health, and system info. It also owns the local theme preference.
- `src/api/client.ts` is the single fetch boundary. It injects an in-memory bearer token when the user supplies one and normalizes API errors.
- Views call real endpoints; there is no mock data layer in production.
- Run detail polls every 1.4 seconds, appends events by durable ID, and stops on terminal statuses.
- The UI uses a custom CSS design system (Instrument Sans, Newsreader, IBM Plex Mono) with no component library.
- Onboarding redirects first-time users to `/welcome`; the welcome flow can be replayed from Settings.

## Concurrency and failure handling

- `JobRunner` is a bounded local executor; rejected work fails the request rather than disappearing.
- Approval resolution uses a conditional claim so two concurrent approvals cannot both resume the same run.
- File moves are re-checked immediately before the operation; a changed source or occupied destination produces a conflict instead of an overwrite.
- SQLite writes use WAL and a busy timeout; the app is intended for one local user, not concurrent multi-user load.
- Startup marks interrupted runs as failed, seeds missing examples, and creates the synthetic demo folder. Startup seeding failures are logged without blocking the API.

## Extension points

To add a new action safely:

1. Add a descriptor and parameter schema to `ActionRegistry`.
2. Implement the action in `RunExecutor` using `PathGuard` and `SafeFileOperations` for any filesystem access.
3. Add validator coverage and an integration test.
4. Update the workflow editor/action metadata if the UI needs a custom form.
5. Document the action in `docs/api.md`.

The registry is intentionally closed. There is no plugin loading, dynamic classpath scan, shell action, or model-supplied executable step.
